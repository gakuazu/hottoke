## 結論（先に要点）

**実装は進めて問題ないが、依頼文・過去ドキュメントに1点重要な事実誤認があるため、最初に訂正する。**

> 依頼文には「1本目はCoreImage/Metalでの模様生成を実装済みの実績がある」とあるが、実際に`app/`のコードを読んで確認したところ、**1本目「カレイド日記」はCore Image・Metal・CIKernelを一切使っていない**。`KaleidoscopeRenderer.swift`はCore Graphics（`CGContext`への直接描画）だけで模様を生成しており、`app/`全体を`grep`しても`CIKernel`/`CIFilter`/`Metal`/`MTKView`のいずれも1件もヒットしない（`docs/13-app2-feasibility-review.md`にも同様の誤記があり、今回合わせて訂正する）。

これは「実績があるから大丈夫」という楽観を一段引き下げる事実であり、**このアプリで初めてCore Imageカスタムカーネル／SpriteKit物理を使うことになる**という前提でリスクを見積もる必要がある。そのうえで見立てを述べると:

- 仕様書2.2節の「高さマップ蓄積→法線再構成→陰影合成」という**アプローチ自体は技術的に健全**で、むしろ**手書きのCIKernelを書く前に検討すべき、もっとリスクの低い実現方法（Core Imageの組み込みフィルタ`CIHeightFieldFromMask`＋`CIShadedMaterial`の組み合わせ）がApple標準で存在する**ことを見つけた（1章で詳述）。これを使えば「手書きGPUシェーダーをこのチームで初めて書く」リスクをほぼ回避できる。
- SpriteKitの物理エンジン自体は傾き操作のtilt-mazeパターンとして枯れているが、**SpriteKitの描画（SKView）とCore Imageの描画を同じ画面で毎フレーム合成する」構成は素直にやると難所になる**。SpriteKitは物理計算専用（非表示）で使い、玉の見た目は別レイヤーで自前描画する構成を推奨する（2章）。
- GitHub Actionsでは**コンパイル・ユニットテスト・IPA生成は検証できるが、傾き操作の「手触り」と陰影の「見た目の説得力」の両方は実機でしか判断できない**。これは仕様書9章の認識と一致するが、このアプリは2本目（ARKit）よりもさらに「実機でしか検証できない核」の比率が高いアプリだと評価する（3章）。
- ワイヤーフレームの画面構成自体はSwiftUI標準コンポーネントで無理なく実装できる。ただし**保存画面の4:5/9:16書き出しが「正方形キャンバスをどう収めるか」を明記しておらず、これを決めないと実装できない**という具体的な仕様ギャップを見つけた（4章）。
- 「インスタ映え最優先でMVPも妥協しない」という方針は、**妥協せずに狙って良いと判断する**。ただし1本目・2本目よりも実機での調整ラウンド数を多めに見積もるべきで、「何回か実機で見てオーナーに判断してもらう」前提を最初から計画に入れておくことを強く推奨する（5章）。

## 1. Core Imageカスタムカーネルによるリアルタイム高さマップ陰影は実機で無理なく動くか

### 1.1 最重要の発見: 手書きCIKernelより低リスクな実現方法がある

仕様書2.2節は「CIKernelで①高さマップ蓄積、②法線再構成＋陰影合成、の2つを自前で書く」設計になっているが、Core Imageには**この用途専用の組み込みフィルタが存在する**。

- `CIHeightFieldFromMask`: グレースケール（マスク）画像を滑らかな高さマップへ変換する組み込みフィルタ。
- `CIShadedMaterial`: 高さマップ画像と「シェーディング画像（法線方向→色のルックアップ、いわゆるmatcap/light-probe的な画像）」を渡すと、法線を内部で再構成して陰影を合成した画像を返す組み込みフィルタ。

この2つを繋げば、仕様書2.2節が「自作CIKernelで」と書いている②の工程（法線再構成＋陰影合成）をApple純正の実装に丸ごと置き換えられる。さらに①の「高さマップ蓄積（玉の軌跡をガウシアン状の筆で彫る）」工程も、**1本目`KaleidoscopeRenderer`と同じ手法（`CGContext`にぼかした白い円を描き重ねる）をそのままグレースケールのオフスクリーンバッファに対して使えば実現でき、CIKernelを一切書かずに済む可能性がある**。

この構成が現実的な道筋だと判断する理由:
- 1本目で実証済みの「CGContextへの描画」技術をそのまま転用できる（①の部分は新技術ゼロ）。
- ②の部分は自前でMetal Shading Language相当のコードをこのチームが初めて書くリスクを回避できる（Apple側で最適化済みのGPUパスに乗る）。
- `CIShadedMaterial`の「シェーディング画像」は光源方向・色味を自由に作り込めるため、仕様書2.3節の「暖色寄りの単一方向光」「何度もなぞった場所ほど際立つコントラスト」は、シェーディング画像側のデザインと高さのスケール係数の調整で狙える可能性が高い。ただし組み込みフィルタは汎用的な「matcap的ルックアップ」であり、仕様書が想定する厳密なランバート反射＋スペキュラとは数式的に同一ではないため、**見た目が仕様書のイメージ通りになるかは実機でのプロトタイプで確認が必須**（5.1節の提案と合わせて最優先で検証する）。
- どうしても狙った陰影にならない場合のフォールバックとして、仕様書が元々想定していた「自作CIKernelで法線再構成＋ランバート計算」にいつでも切り替えられる（組み込みフィルタを試すことは後戻りできない投資ではない）。

### 1.2 「蓄積（前フレームの状態を引き継ぐ）」特有の注意点

Core Imageは基本的に「入力画像→フィルタ→出力画像」の**無状態な関数型パイプライン**であり、「前フレームの高さマップに今フレームの筆跡を加算して次フレームに引き継ぐ」という**状態を持つ蓄積**はCore Imageの標準的な使い方からは一段外れる。具体的には:

- 毎フレーム「前回の高さマップ画像」を入力として使い、そこに新しい筆跡を合成した結果を**明示的に`CIContext.render(to:)`でCVPixelBuffer等の具体的なバッファへ焼き込む**必要がある。これを怠って`CIImage`のフィルタ連鎖をチェーンのまま次フレームに渡し続けると、Core Imageの内部的な処理グラフ（遅延評価のノード木）が毎フレームどんどん伸びていき、時間が経つほど重くなる／クラッシュするという典型的な落とし穴がある（Core Imageを使ったことがある人には既知の注意点だが、このチームにとっては初めて踏む可能性がある罠）。対策は明確（毎フレーム必ず確定的なバッファに焼き込んで「リセット」する）だが、実装時に明示的に意識して設計する必要がある。
- 仕様書2.3節の「ダーティ領域だけ更新」は、Core Imageの`CIKernel.apply(extent:roiCallback:)`や`CIImage`の`extent`ベースの設計と相性が良く、**Core Imageが得意な部分に乗っている提案**だと評価する。全画面を毎フレーム再計算しない設計はCore Imageの思想そのものなので、この方向性は妥当。

### 1.3 パフォーマンスの見立て

- 512〜1024px角のグレースケール高さマップに対する「筆の合成」「`CIHeightFieldFromMask`」「`CIShadedMaterial`」はいずれもこの解像度では軽量なフィルタで、直近5〜6年のiPhone（Sideloadly配布の前提である本人・家族の実機がこの範囲であれば）で60fpsは無理なく狙えると見立てる。不安要素があるとすれば「毎フレームのCIContext.render呼び出し自体のオーバーヘッド」と「蓄積バッファのCPU/GPU間コピーコスト」であり、これは机上で確実とは言えないため**実機での計測が必須**（3章）。
- 1本目のUIView設計（扇形ビットマップをバックグラウンドキューで再生成し、メインスレッドの描画は常にキャッシュ済みの画像を使う）と同じ「重い再計算と軽い表示更新を分離する」考え方をこのアプリにも転用できる。具体的には、高さマップの更新（蓄積＋シェーディング）を毎フレームではなく一定間隔（例: 30〜60Hzの範囲で調整）に間引き、玉自体の表示位置だけは毎フレーム滑らかに動かす、という分離を検討する価値がある。

## 2. SpriteKitでの玉の物理シミュレーションの難所

- **傾き→物理ボディへの力の反映自体**（`CMMotionManager.deviceMotion`の重力ベクトルをSpriteKitの`SKPhysicsBody`への力・加速度として適用する）は、tilt-maze系アプリで広く使われる枯れたパターンで、技術的な不確実性は低い。`linearDamping`・`restitution`（壁での低反発）・速度クランプ（`update(_:)`内で`physicsBody.velocity`の大きさを手動で制限）もSpriteKit標準機能の範囲内で実装できる。
- **最大の難所は物理そのものではなく、SpriteKitの描画とCore Imageの描画を同一画面で毎フレーム合成する構成**だと判断する。ワイヤーフレーム（画面2）は「砂キャンバス（Core Image陰影）の上に玉（スプライト）を重ねる」前提だが、これを素直に「`SpriteView`でSKSceneをそのまま表示し、その中に砂キャンバスのテクスチャも置く」と実装すると、SpriteKit自身のMetalレンダラーとCore ImageのCIContextレンダラーという**2つの独立したGPUレンダリングパスを毎フレーム同期・合成する**ことになり、座標系変換（SpriteKitのシーン座標とCore Imageのピクセル座標）のズレや二重コストの原因になりやすい。
  - **推奨する設計**: SpriteKitの`SKScene`は**画面に表示しない「物理専用エンジン」として裏で動かす**（`SKView`を使わず、`SKPhysicsWorld`＋玉1個の`SKPhysicsBody`だけを持つシーンを`update(_:)`ごとに進め、玉の位置・速度だけを取り出す）。画面に見える玉の描画自体は、砂キャンバスの陰影合成と同じレンダリングパス（SwiftUIのオーバーレイ、または同じCIContext合成の中）で行う。これにより「2つの独立した描画システムを画面上で重ねる」難所そのものを回避できる。SpriteKitは「物理エンジンだけを借りる」という使い方に限定すれば、過去2本で実績がないことの不確実性も小さく抑えられる。
- **軌跡の補間**: 仕様書2.2節は「玉の位置に追従して…彫る」とだけ書かれているが、玉が速く動くフレームでは前フレーム位置と今フレーム位置の間に隙間ができ、溝が点線状に途切れるリスクがある。前フレーム位置から今フレーム位置までを線分（またはスプライン）で補間してスタンプする実装が必要になる点を、具体的な実装時の注意点として追記することを推奨する。
- **軸の向きの取り違え**: `deviceMotion`の重力ベクトル（デバイス座標系）を画面上の左右・上下にマッピングする際、インターフェース向き（縦持ち固定と想定）との対応を誤ると「傾けた方向と逆に玉が動く」バグになりやすい。2本目「かおゲー」で実際に踏んだ「ウインク左右反転」バグ（`docs/04-build-log.md`関連のビルドログ参照）と同系統の座標系の取り違えであり、**実機での最初の動作確認で真っ先にチェックすべき項目**として明記しておく。

## 3. GitHub Actionsで検証できること／実機必須になること

既存の`.github/workflows/ios-build.yml`（シミュレータ向けビルド・ユニットテスト・署名なしIPAパッケージングとArtifactアップロード）はそのまま転用できる。このアプリに対して具体的に当てはめると:

**CIで検証できる**:
- コンパイルが通ること（CIKernel/組み込みフィルタの呼び出しコード、SpriteKit物理コード、SwiftUI画面一式）。
- 傾き・物理・減衰・クランプ・深さの加算とクランプ・アスペクト比クロップ矩形の計算など、**CoreMotion/SpriteKit/Core Imageの実体に依存しない純粋なSwift関数**として切り出した部分のユニットテスト（1本目`KaleidoscopeLogicTests`と同じ戦略。例えば「重力ベクトル→目標速度への変換関数」「深さの加算クランプ関数」「正方形→4:5/9:16クロップ矩形を計算する関数」は、CoreMotionやSpriteKitの実機依存から切り離して素直にXCTestにできる）。
- 署名なしIPAの生成そのもの。

**実機必須（シミュレータ・CIでは判断不可）**:
- 傾き操作の「手触り」（デッドゾーン・慣性・摩擦のパラメータが気持ちいいかどうか）。`CMMotionManager`はシミュレータでは実際の傾き入力が得られない（仕様書9章の記述通り）。
- 陰影の「見た目の説得力」（溝に見えるか、ただのぼやけた線に見えないか）。これはシミュレータでもCore Imageのレンダリング自体は動く（Appleシリコン搭載Macのシミュレータは実際にGPUでレンダリングするため、静止画としての見え方は確認できる）が、**実機の画面サイズ・光の下での見え方、かつ60fpsで動き続けた時の見え方**は実機でしか判断できない。
- 実機での実際のフレームレート計測（Core ImageのCPU/GPU間コピーコスト、SpriteKit物理との同時実行時の負荷）。

2本目（ARKit）の知見（`docs/13-app2-feasibility-review.md`）では「シミュレータでは顔トラッキングの入力自体が一切得られない」という制約だったが、このアプリは**入力（傾き）も出力の質（陰影の説得力・fps）も両方実機依存**という点で、検証の実機依存度は2本目よりもさらに高いと評価する。1本目の視覚調整承認フロー（`docs/03b-visual-prototype-learnings.md`相当のプロセス）を、このアプリでも早期から前提に入れておくべきだと考える。

## 4. ワイヤーフレームの画面構成はSwiftUIで無理なく実装できるか

結論として**大部分は無理なく実装できる**。具体的に screen-by-screen で確認する。

- **画面1 オンボーディング／画面2 メイン操作画面**: 正方形キャンバス自体は`.aspectRatio(1, contentMode: .fit)`で素直に実装できる。懸念はなし。
- **画面2a 「ならす」確認ダイアログ**: `.confirmationDialog`で標準実装可能。懸念はなし。
- **画面3 保存/共有画面**: ここに**仕様のギャップ**を見つけた。仕様書5.1節・ワイヤーフレームはいずれも「1:1/4:5/9:16の3種類で書き出す」と書いているが、**庭のキャンバス自体は正方形（11章で確定済み）**であるため、4:5・9:16のような縦長比率で書き出す際に「正方形の絵をどう収めるか」が未決定である。選択肢は大きく2つあり、見た目が大きく変わる:
  1. **中央クロップ**: 正方形の絵の上下（または左右）を切り落として縦長にする。9:16の場合、幅方向で見ると絵の約44%が画面外に切れる計算になり、陰影の構図（玉の軌跡の全体像）が崩れる可能性が高い。
  2. **パディング**: 正方形の絵はそのまま使い、上下（または左右）に背景色・砂の質感の余白を追加して縦長にする。絵自体は欠けないが、Instagram Stories等で見た際に「正方形の絵に余白がついている」見え方になる。
  
  「インスタ映え」が最重要要件である以上、**クロップで溝の構図が欠けることは避けたい**ため、パディング方式（またはズーム度を選べるクロップ＋パディングの併用）を基本方針として提案したい。この点は実装前にオーナー確認が必要な具体的な論点として5章に記載する。
- **画面4 ギャラリー／4b 詳細**: 1本目`ArchivePatternStore`のJSON＋画像ファイル構成をそのまま転用でき、懸念はなし。
- **画面5 設定／画面6 課金**: 1本目・2本目と同じ`Form`/`List`構成、StoreKit2のペイウォールパターンの転用であり、懸念はなし。

## 5. 懸念点・仕様修正の提案（まとめ）

1. **（要オーナー確認）保存画面の4:5/9:16書き出し方式**: 4章で述べた「クロップかパディングか」を決めないと実装に着手できない。ios-engineerとしては構図を保つパディング方式を推奨するが、見た目の好みが関わるため実機プロトタイプで両方試してオーナーに見てもらうことを提案する。
2. **（実装方針として提案、仕様変更ではない）陰影合成は手書きCIKernelより先にApple組み込みフィルタ（`CIHeightFieldFromMask`＋`CIShadedMaterial`）を試す**: 1.1節で述べた通り、これが狙った見た目に届くなら実装コスト・リスクを大きく下げられる。届かない場合は仕様書が元々想定していた自作CIKernelにフォールバックする、という2段構えを最初の着手順として明記しておきたい。
3. **（実装方針として提案）SpriteKitは非表示の物理エンジンとしてのみ使う**: 2章で述べた「SKSceneを画面に出さず物理計算だけ借りる」構成を最初から採用し、SpriteKitとCore Imageの二重レンダリング合成という難所を避ける。
4. **（実装の注意点として明記）軌跡の補間と軸の向き**: 2章で述べた「速い動きでの溝の途切れ」「傾き方向の取り違え」は、仕様書の記述粒度ではまだ抜けているため、実装時の明示的なチェック項目としてテストケース・実機確認項目に入れる。
5. **（事実訂正）1本目はCore Image/Metalの実績はない**: 冒頭で述べた訂正。`docs/13-app2-feasibility-review.md`にも同種の誤記があるため、今後この前提を引用する際は訂正後の認識（1本目はCore Graphics、CIKernel/Metalはこのアプリが初）で扱ってほしい。

### 「インスタ映え」最優先要件に対する正直な見立て

**MVPで妥協せず狙って良いと判断する。** 理由は、仕様書2.2節の「CIKernelで高さマップ＋陰影」というアプローチそのものは枯れた技術（ハイトフィールド法線再構成は古典的手法）であり、かつ1.1節で見つけた組み込みフィルタのルートを使えば「このチームが初めて書く自作GPUシェーダー」という最大の不確実性を回避できる可能性が高いため。**簡略化すべきなのは技術的アプローチではなく、検証・調整のスケジュール感**だと考える。具体的には:

- 陰影の見た目の説得力は、1本目の模様調整（`docs/03b-visual-prototype-learnings.md`）や2本目のブレンドシェイプ閾値調整よりも**さらに「実機で見て、気持ちよくなければ数値を変えてもう一度実機で見る」というラウンド数が多くなる**可能性が高い。Sideloadlyの署名が7日で失効する制約もあるため、1回のビルド→配布→確認サイクルのコストが地味に積み重なる点を最初から見込んでおきたい。
- 先に1.1節の「組み込みフィルタ＋静止画プロトタイプ」だけをシミュレータ上で素早く試し（物理・傾きは関係ないので実機を使わなくても見た目の方向性だけは確認できる）、方向性が固まってから「実機での物理・傾きの手触り調整」フェーズに進む、という**2段階の検証順序**を取ることで、実機を使う調整ラウンドの回数自体は抑えられると見立てている。

以上を踏まえ、**仕様・ワイヤーフレームのまま実装着手して問題ない**が、4章のアスペクト比の論点だけは着手前にオーナー確認を挟むことを推奨する。
