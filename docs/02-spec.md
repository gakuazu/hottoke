## 1. コンセプト概要

### 1.1 アプリの仮称と一言コンセプト

**仮称: 「カレイド日記（Kaleido Diary）」** ※正式名称・ブランディングは未確定。ASO余地の検討はaso-marketerフェーズで別途行い、本書では「わかりやすい仮称」として扱う。

一言で言うと：**「iPhoneが1日中静かに記録している活動データを、毎日1本の万華鏡模様の動画として自動生成する日記アプリ」**。歩数計や活動量計のような「数字で管理する」アプリではなく、「その日のリズムを模様として眺めて味わう」アプリという立ち位置を取る。

### 1.2 コア体験（2モード構成）

**モード1: 日替わり活動データ模様動画（メイン機能）**

- iPhoneのモーションコプロセッサーが端末内でバックグラウンド常時記録している1日分の活動データ（`CMPedometer`: 歩数・距離・登った階数、`CMMotionActivityManager`: 静止/歩行/走行/自転車/車移動の時間帯別区分）を取得し、その日を象徴する数十秒（目安30秒前後）の模様変化動画をその場でオフライン生成する。
- Wordleのような「今日の1つ」的な日替わりの儀式性を持たせる。
- 設計の核: 単純な合計値（歩数◯歩など）を1パラメータ化するのではなく、**1日の活動強度の時系列カーブそのものを模様のテンポ変化としてアニメーションに反映**する。動画を見返すだけでその日の生活のリズムが感覚的に蘇ることを狙う。
- 活動量が少ない日は「物足りない日」ではなく「静けさの美しい模様」として肯定的に演出する。歩数目標未達を煽るような罪悪感訴求は行わない（案4 No-Buyトラッカー検討時に確認した反省点を踏襲）。

**モード2: 手動クリエイティブモード（副機能）**

- CoreMotion（加速度計・ジャイロ）を使い、端末を**振ると模様がシャッフル**、**傾けると模様が回転**する、本物の万華鏡の身体的操作感を再現する。
- スライダーによる対称数・カラーパレット・速度の手動調整も併用できる。
- 「振って偶然の模様に出会う」体験と「スライダーで作り込む」体験の両立が差別化ポイント。

### 1.3 確定している非採用事項

| 検討した案 | 判断 | 理由 |
|---|---|---|
| 音楽・マイク反応モード | 不採用 | 既存の音楽ビジュアライザー系アプリ（Vibe Flow等）との直接競合を避けるため |
| 生成AI（Foundation Models等）の利用 | 不採用 | Apple Intelligence非対応機種でも動作させることを優先。全iPhoneで動くことをコンセプトの前提とする |

### 1.4 重要な技術的制約（誠実に明記する）

- **iOSはサードパーティアプリがホーム画面/ロック画面の壁紙そのものをリアルタイムに書き換え続けるAPIを公開していない。** そのため「壁紙に設定した状態でアプリを閉じても動き続ける」ことは実現できない。
- したがって体験の主軸は**アプリ内で見る・作る**ことであり、壁紙への反映は「お気に入りの瞬間をLive Photo/静止画として書き出し、iOS標準の壁紙設定フローに手動で渡す」副産物的機能という位置づけになる。ストア掲載文・アプリ内説明の両方でこの前提を誤解のないように明記する（誇大な「ライブ壁紙」表現は審査・レビュー炎上リスクにもなるため厳禁）。
- 妥協案として、**WidgetKitのロック画面ウィジェット**で時間帯ごとの模様スナップショットを表示することは可能（iOS 17標準の万華鏡壁紙と同様、時間経過で自動的に絵柄が切り替わる仕組み）。これはv2以降の検討事項とする（4章参照）。

## 3. データ取得〜動画生成ロジック詳細

### 3.1 全体の処理フロー

1. アプリ起動時（または「今日の模様」画面を開いた時）、`CMMotionActivityManager.queryActivityStarting(from:, to:, to:, withHandler:)` で当日0時〜現在時刻までの活動区間（タイムスタンプ付き、種別: stationary/walking/running/automotive/cycling/unknown）を取得する。
2. `CMPedometer.queryPedometerData(from:to:withHandler:)` で同期間の歩数・距離・`floorsAscended`（登った階数）を取得する。
3. 活動区間を時間帯（朝/昼/夕方/夜）に振り分け、各区間に「動きの種類パラメータ」と「色パレットパラメータ」を割り当てる（3.2節・3.3節のマッピング表）。
4. 得られたタイムライン（区間ごとのパラメータ列）を、動画の総尺（目安30秒）にタイムラプス的に圧縮・補間し、Metal/CoreImageのシェーダーに渡すキーフレーム列を作る。
5. `AVAssetWriter` でフレームごとにレンダリングした画像をエンコードし、mp4動画としてアプリのサンドボックス内に保存する（この時点ではまだカメラロールには保存しない）。
6. ユーザーが「保存」を選んだ時点で、`PHPhotoLibrary` 経由でカメラロールに書き出す。

**技術メモ（重要）**: `CMMotionActivityManager` はOS側のモーションコプロセッサーが端末にアプリの有無に関わらず継続記録しているデータを保持しているため、**その日の朝からアプリを開いていなくても、起動した瞬間にその日の朝〜現在までの履歴を遡って取得できる**（万歩計アプリが未インストール時の歩数も遡って表示できるのと同じ仕組み）。ただしOSが保持する履歴は数日〜1週間程度が目安であり、無期限に遡れるわけではない点は留意する。

### 3.2 「何をしていたか」→ 模様の動き方マッピング表

| 活動種別（`CMMotionActivityConstants`） | 模様の動きのイメージ | 実装パラメータの方向性（例） |
|---|---|---|
| stationary（静止） | ゆったり回転する瞑想的な模様 | 回転速度: 低・一定／変形強度: 低／ノイズ揺らぎ: 微小 |
| walking（歩行） | 歩行ケイデンスに合わせた一定リズムの拍動 | 拍動周期を歩行ケイデンス（歩/分の推定値）に同期／変形強度: 中・周期的 |
| running（走行） | 速く激しい変形 | 回転速度・変形速度: 高／要素の分裂・再結合を頻繁に |
| automotive（車移動） | 要素が流れるようなスライド | 模様全体を一定方向に流すオフセットアニメーション／回転は控えめ |
| cycling（自転車） | 回転運動の強調 | 回転速度: 中〜高・滑らか／歩行より一段階強い規則的な回転 |
| floorsAscended（階段、CMPedometer由来） | 中心から外側・上方向への広がり | 検出区間で放射状の拡大アニメーションを重ねる（他の動きに加算するオーバーレイ的な演出） |
| unknown / データなし | 静止に準じる控えめな模様 | stationaryに近い低強度パラメータをデフォルトとして使用 |

### 3.3 「いつだったか」→ 色パレットマッピング表

| 時間帯（目安） | 色のイメージ | 実装方向性（例） |
|---|---|---|
| 朝（〜10時頃） | 淡いパステル／オレンジ〜ピンク | 低彩度・高明度のグラデーション |
| 昼（10時〜16時頃） | 彩度高い青〜黄 | 高彩度・高コントラストの配色 |
| 夕方（16時〜19時頃） | オレンジ〜赤紫 | 夕焼け調のグラデーション、彩度中〜高 |
| 夜（19時〜） | 藍〜紫の発光調 | 低明度背景に発光的なハイライト色を乗せる |

### 3.4 動画の時間軸設計

- 動画の前半＝朝、中盤＝昼、終盤＝夜、という構成で1日の時系列をそのまま圧縮する。
- 活動データがまだ記録されていない時間帯（例: 午前中にアプリを開いた場合の午後〜夜の分）は、動画生成時点までのデータのみで生成し、日をまたいで「完成版」に更新されるのではなく**その時点のスナップショットとして1本を確定させる**（1日1回、最後に開いたタイミング、あるいは明示的な「今日の模様を生成する」操作で確定するかは4章のオープン論点参照）。
- 就寝中などデータがほぼ変化しない時間帯は、圧縮した時間軸の中で「静けさの模様」区間として自然に短く扱われるよう、活動区間の長さではなく相対的な活動強度でタイムラプスの重み付けを行う（単純な等時間割り当てだと就寝時間が長すぎて間延びするため）。

### 3.5 【2026-08-29更新】模様の描画方式を「数学模様」4スタイルに変更

実機テストで「ガラス片を敷き詰める」旧方式の見た目に強い不満（ダサい、キラキラしない等）が出たため、模様そのものを4種類の「数学模様」に置き換えた。ブラウザ上のプロトタイプでオーナーと繰り返し検証し、明示的な承認を得た上でSwift実装に移植している。

**4スタイル**:
- 幾何学タイル（tiling）: 三角格子の上に5種類の幾何学モチーフ（八芒星・六芒星・六角の二重輪・正方形+円・花びら）をハッシュ値で振り分けて敷き詰める
- スピログラフ（spirograph）: 歯車のような曲線を3〜6層重ね、中心が空洞にならないよう層の配置と発光コアを工夫
- 波の干渉（waves）: 複数周波数のサイン波を重ねた輪を何層も描き、輪の間を薄く塗って帯にし、波の頂点にきらめきを添える
- フラクタル分岐（fractal）: 中心近くからすぐ枝分かれする木構造を再帰的に描く

**「何をしていたか」→ 模様スタイルのマッピング**（3.2節のマッピング表を補足するもの。動きのパラメータ表とは別軸で、どの模様を使うかを決める）:

| 活動種別 | 模様スタイル | 理由 |
|---|---|---|
| stationary（静止） | 波の干渉 | 穏やか・滑らかな動きに合う |
| unknown（不明） | 波の干渉 | 同上（stationaryに準じる） |
| automotive（車移動） | 波の干渉 | 同上 |
| walking（歩行） | 幾何学タイル | 規則的な歩行リズムに合う |
| cycling（自転車） | スピログラフ | 歯車のような回転運動に合う |
| running（走行） | フラクタル分岐 | 激しく分岐するエネルギーに合う |

「今日の模様」動画は1本の中でスタイル自体が何度も切り替わると忙しない見た目になるため、その日いちばん長く続いた移動系の活動（`dominantMovingKind`）から動画全体で使うスタイルを1つに決める。密度・複雑さの方はセグメントごとの活動の強さに応じて動画内でも変化させる。

**動的な揺らぎ（呼吸するアニメーション）**: 単に模様が回転するだけでなく、(1) 密度・複雑さが基準値を中心にゆっくり呼吸するように増減する、(2) 模様全体がゆっくりズームイン・アウトする、(3) 回転速度自体も一定ではなく緩やかに加速・減速し、たまに一瞬だけ逆回転することもある、という3種類の時間変化をプロトタイプの数式のまま移植した（`KaleidoscopeDynamics`）。これにより「ただ回っているだけ」に見えないようにしている。

## 4. MVP（v1）のスコープとv2以降の切り分け

前提: オーナーは非エンジニア、実装はAIエージェント（ios-engineer）が担当し、ビルドはGitHub Actions、配布はSideloadly（実機のみ・7日で署名失効）。この体制で「まず動くものを早く実機で確認できる」規模感を優先する。

### v1（MVP）に含める

- オンボーディング（権限説明、初回の「今日の模様」自動生成体験）
- 「今日の模様」画面：当日データの取得・マッピング・動画生成・ループ再生
- 手動クリエイティブモード：シェイク/傾き操作＋基本スライダー（対称数・パレット3〜4種・速度）
- 保存：動画（mp4）・静止画（1フレーム）のカメラロール書き出し
- 壁紙設定への案内（アプリ内で直接設定はできない旨の明記＋手順ガイド）
- 設定画面簡易版（権限状態確認・プライバシーポリシー表示）
- 課金UIの土台のみ（StoreKit Configurationでのローカルテスト。実販売はv2でApple Developer Program登録後）

### v2以降に回す

- 過去の模様アーカイブ（ローカルDB永続化、カレンダービュー）
- Live Photo書き出し（静止画+動画のペアリング処理）
- 4K書き出し
- 追加カラーパレット・高度パラメータ（サブスク訴求の中核機能）
- サブスクの本実装・実販売（Apple Developer Program登録後）
- WidgetKitロック画面ウィジェット
- ローカル通知（「今日の模様ができました」）
- 買い切りオプションの実装（5章参照、要検討）

### 判断理由

- 「動画生成エンジン」（データ取得→マッピング→レンダリング→書き出し）がこのアプリの技術的な核であり、ここが動かなければ他の全機能が意味を持たない。v1はこの核を最優先で完成させ、周辺機能（アーカイブ・ウィジェット・詳細課金）は後回しにする。
- 過去アーカイブとサブスクの本実装は、Apple Developer Program登録（年$99）というオーナー側の予算判断が必要な決定と連動するため、CLAUDE.mdの運用ルール（予算を伴う判断は事前確認）に沿ってv2として明確に切り離す。
- Live Photo生成は「静止画と3秒程度の動画をペアリングするメタデータ処理」が別途必要で、単純な動画/静止画保存よりも実装・デバッグの手間が大きい。v1では価値検証を優先し、動画そのものの保存で代替する。

## 5. 収益モデルの最終提案

### 5.1 基本方針: 基本無料＋サブスク（主軸）

`docs/01-idea-shortlist.md` 案5で示されたWidgetsmithの実績（RevenueCatケーススタディで月$200k規模、最盛期月$3M）を踏まえ、**パーソナライズ・日課系コンテンツに対するサブスクモデルの実績は裏付けがある**。本アプリは「毎日1本」という日課性が強く、継続利用・継続課金と相性が良いためサブスクを主軸とする。

**無料で使える範囲**:
- 今日の模様の自動生成・再生・1回分の保存（動画・静止画）
- 手動クリエイティブモードの基本パレット（3〜4種）・基本スライダー

**サブスクで解放する範囲**:
- 高度なパラメータ（周波数・ノイズ強度・多層合成など）
- 追加カラーパレット（季節限定・特別パレット等の継続的な追加コンテンツ）
- 4K書き出し
- 過去の模様アーカイブの閲覧（日課性・愛着形成の核であり、最も強いサブスク継続動機になりうる）

### 5.2 買い切りオプションについて

案5の検討過程では買い切りモデルの言及はなく、Widgetsmith型の継続課金コンテンツ（毎月新しいパレット等が増える）と相性が良いため、サブスクを主軸とすることが妥当と判断する。ただし以下の理由から、**小規模な買い切りオプションを補助的に併設することを提案する**。

- サブスク疲れ・サブスクへの心理的抵抗が一定数存在する（案8の割り勘アプリ検討時にも同様の傾向を確認）。
- 「毎日使うほどではないが、たまに使う」ライトユーザー層を取りこぼさないため、**買い切りの「パレット追加パック」を単発購入できる小口オプション**を用意する（アーカイブ・4K書き出しなどの継続的価値提供機能はサブスク限定のまま維持する）。

まとめると、**サブスクを収益の主軸としつつ、パレット単体の買い切りオプションをサブスクに入らない層への入口として併設**する二段構えを提案する。価格帯・具体的なプラン設計はオーナー確認事項とする（7章）。

### 5.3 技術・コスト面の補足

- 現時点でApple Developer Program未登録・予算ほぼゼロのため、サブスク管理はサードパーティ（RevenueCat等）の利用料が発生しないネイティブ**StoreKit 2**での実装を推奨する。サーバー不要でエンタイトルメント管理が完結でき、本プロジェクトの「サーバーレス・端末内完結」方針とも一致する。
- 実際の課金導線・価格表示のテストはApple Developer Program登録前は「StoreKit Configuration」ファイルによるローカルサンドボックスに限定される（CLAUDE.md記載の既定方針どおり）。実売上の発生は登録後。

## 6. プライバシー・審査ガイドライン上の留意点

- **Motion & Fitness権限**: `NSMotionUsageDescription` の許可理由文言で、「今日の活動データから模様を作るために使う」「データは端末外に一切送信しない」ことを明確に説明する。オンボーディング画面でも同様の訴求を行い、権限リクエストダイアログ表示前に価値を理解してもらう（審査ガイドライン5.1.1のデータ最小化・目的説明の観点にも合致）。
- **写真ライブラリへの書き込み権限**: 保存機能のために `NSPhotoLibraryAddUsageDescription` が必要（追加のみであれば読み取り権限は不要な設計にできる）。
- **HealthKitは使用しない**: `CMPedometer`/`CMMotionActivityManager` はHealthKit経由ではなくCoreMotionから直接取得するため、HealthKit特有の追加審査要件（entitlement申請等）は発生しない。この点は明示的に設計上の選択として記録しておく。
- **データを端末外に送信しない**という設計そのものが差別化・訴求ポイントであるため、App Store Connectの「プライバシー」欄（Appのプライバシー情報）は「データは収集されていません（Data Not Collected）」で申告できる設計を維持する。実装時にクラッシュ解析SDKや広告SDKを安易に追加するとこの申告が崩れるため、追加する場合は都度この方針との整合を確認する。
- **壁紙表現の誇大広告防止**: 「ライブ壁紙」「壁紙が動く」といった表現は、実際にはアプリを開いている間のみの体験であるため、ストア掲載文・アプリ内表現ともに正確を期す（1.4節の制約を参照）。誤解を招く表現は審査リジェクト（ガイドライン2.3.1 虚偽の説明）やユーザーからの低評価レビューの直接原因になりうる。
- **サブスク表示の必須要件**: サブスク購読画面には価格・期間・自動更新の明記、復元購入ボタン、プライバシーポリシー・利用規約へのリンクを購入前に表示する（ガイドライン3.1.2）。v1では課金導線自体は用意するが実売なしのため、v2で実装する際に改めてチェックする。
- **年齢制限・不快コンテンツ該当なし**: 生成される模様は幾何学模様のみで、ユーザー生成コンテンツの投稿・共有機能もない（v1時点）ため、コンテンツモデレーション関連のガイドライン対応は不要と判断する。

## 7. オープンな論点・オーナーに確認すべき事項

1. **正式名称・ブランディング**: 本書では「カレイド日記（仮称）」としているが、正式名称はaso-marketerフェーズでの検討に委ねるか、オーナーの意向を先に確認するか。
2. **【オーナー決定・2026-08-26→2026-08-29に変更】「今日の模様」の確定タイミング**: 当初は1日1回だけ生成・確定し同日中の再生成はしない方針（Wordle的な儀式性を重視）だったが、実機テストで「時間が経って活動しても更新されないのが不便」とのフィードバックがあり変更。**同じ日でもアプリを開き直した時点で前回確定時から歩数などの活動量に変化があれば自動で作り直す**（変化がなければ確定済みの模様をそのまま見返す）。加えて画面右上に手動更新ボタンを設置し、いつでも明示的に最新データで作り直せるようにした。
3. **【オーナー決定済み・2026-08-26】データが少ない状況のフォールバック**: 専用のプレースホルダー演出は用意せず、**その時点までの実データでそのまま「静けさの模様」を生成する**（新規インストール当日・寝起きに開いた場合も含め、特別扱いせず一貫したロジックで処理する）。
4. **過去アーカイブの保存期間・容量**: 無制限に動画を溜め続けると端末ストレージを圧迫するため、保持期間（例: 直近30日/90日、あるいは無制限だがサムネイルのみ保持し動画は都度再生成等）の方針をv2設計までに決める必要がある。
5. **サブスク・買い切りの価格帯**: 5章で示した「サブスク主軸＋パレット買い切り併設」の方向性についてオーナーの承認を得た上で、具体的な価格（月額・年額・買い切り単価）を決める。
6. **Apple Developer Program登録のタイミング**: v1（Sideloadly配布のみ）でオーナー・家族による体験検証をどの程度積んでから、年$99の登録・正式配布検討に進むか。
7. **通知機能の要否**: 「今日の模様ができました」的なローカル通知をv2で入れるかどうか。日課化を後押しする一方、通知過多への抵抗感もあるため要検討。
