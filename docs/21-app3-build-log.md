## 2026-09-13: MVP(v1)の土台を実装（プロジェクト作成〜ビルド確認・陰影表現の初期プロトタイプ）

### やったこと（平易な説明）

1. **新しいGitHubリポジトリ`gakuazu/sandgarden`を作成した。**
   1本目・2本目と同じく非公開リポジトリで、`gh`コマンドで作成・クローンした。ビルド・配布の方針（XcodeGenでプロジェクトを組み立て、GitHub Actionsでビルド・テスト、署名なしIPAをSideloadlyでインストール）もこれまでと同じ。

2. **`docs/20-app3-feasibility-review.md`（自分自身が前回書いたレビュー）の推奨をすべて反映した。**
   - **陰影表現は、まずApple純正の組み込みフィルタ（`CIHeightFieldFromMask`＋`CIShadedMaterial`）で作った。** 自分で1から光の計算式を書く（自作CIKernel）方式は使わず、Appleがあらかじめ用意している「グレースケール画像を高さ地図として扱い、光の当たり方を計算して陰影をつける」機能をそのまま利用した。玉が通った場所を少しずつ「彫る」処理は、1本目のカレイド日記で使った「ぼかした円を描き重ねる」方法をそのまま流用した。
   - **玉の物理演算（傾けると転がる・慣性・摩擦・壁での跳ね返り）は、SpriteKit（ゲーム用の物理エンジン）を使わず、自分で書いたシンプルな計算だけで実現した。** レビューでは「SpriteKitを見えない物理エンジンとしてだけ使う」ことを推奨していたが、実際に必要な計算（傾きに応じて少しずつ加速する・徐々に減速する・壁で跳ね返る）はニュートン力学の基本的な計算だけで十分再現できると判断し、SpriteKit自体を使わない、より単純でテストしやすい形にした。これにより「見た目の描画とは別に物理エンジンだけ動かす」という難しい設計を避けつつ、レビューが最も懸念していた「2つの描画の仕組みを画面上で重ねる」問題も最初から発生しない。
   - **「傾けた方向と逆に玉が動く」「速く動いたときに溝が途切れる」という、2本目で実際に踏んだ左右反転バグと同系統のリスクに、最初から対策した。** 傾きの向きの変換や、画面上の位置と実際に「彫る」座標の変換をすべて1か所のファイルにまとめ、それぞれに「何が正しいか」をコメントとテストで固定した。また、玉が速く動いたフレームでも軌跡が途切れないよう、前の位置と今の位置の間を補間して彫る仕組みを入れた。
   - **DEBUGビルド限定の「モックモード」を用意した。** 画面下にスライダーが出て、実際に端末を傾けなくても仮の傾き値を入力できる。これにより、実機がなくてもGitHub Actionsのシミュレータ上で「傾き入力を受け取った後の玉の動き・溝のでき方」を自動テストできる（1本目・2本目と同じ考え方）。

3. **「見た目を実機なしで確認できる工夫」として、小さな確認ツール（PreviewTool）を作った。**
   - 陰影表現の質が今回のアプリで最も重要なので、GitHub Actions上でも見た目をある程度確認できるようにしたいと考えた。
   - 傾き物理・高さ地図の蓄積・陰影合成のロジックを「iOSにしかない機能（画面・カメラ・モーションセンサーなど）に依存しない部分」として`Core/`という場所にまとめ、iOSアプリ本体と、Mac上で動く小さなコマンドラインツール（PreviewTool）の両方から同じコードを使えるようにした。
   - GitHub Actionsのビルド時にこのPreviewToolを実行し、渦巻き状の見本の模様を実際にレンダリングしたPNG画像を3枚（砂質感違い）生成して、Artifact（ビルド結果と一緒にダウンロードできるファイル）としてアップロードするようにした。これにより、オーナーが実機にインストールしなくても、ビルドのたびに「陰影表現がどんな見た目になっているか」を画像で確認できる。

4. **保存・書き出し機能を実装した（1:1/4:5/9:16、パディング方式）。**
   - `docs/20-app3-feasibility-review.md`で指摘していた「正方形の絵を縦長の比率でどう収めるか」という論点は、仕様書側で「クロップ（切り取り）せず、上下に余白を足して正方形の絵をそのまま見せるパディング方式」に決定済みだった。この方式どおりに実装し、「4:5や9:16で書き出しても模様が一切欠けない」ことをテストで確認している。

5. **その他のMVP画面を実装した。**
   - オンボーディング（傾ける→玉が転がる→模様が残る、の3ステップ説明のみ。モーションセンサーは許可ダイアログが不要なため、権限を求める導線はない）
   - メイン操作画面（庭。傾きヒントのトースト、砂/玉の切り替えチップ、「ならす」ボタン、保存ボタン）
   - 「ならす」確認ダイアログ（取り消せないことを明記）
   - 保存/共有画面（アスペクト比選択、標準の共有シート）
   - ギャラリー一覧・詳細（完成画像のスナップショットのみ保存。1本目`ArchivePatternStore`と同じJSON+画像ファイルの構成）
   - 設定画面（砂/玉/BGMのロック表示、モーションセンサーは「許可不要」の表示、写真ライブラリの権限状態、プライバシーポリシー等へのリンク）
   - 課金/ロック解放画面（StoreKit2を使った土台のみ。`Configuration/SandGarden.storekit`によるローカルテスト用の設定ファイルも用意したが、実際の販売はApple Developer Program登録後）

6. **GitHub Actions（自動ビルド）の設定を作った**（`.github/workflows/ios-build.yml`）。1本目・2本目とほぼ同じ仕組みに加え、上記のPreviewToolのビルド・実行・画像アップロードのステップを追加した。

### 苦労した点・実機なしでの工夫

- 最初のビルドで、Core Imageの陰影フィルタがキャンバスの縁だけ不自然に黒っぽくなる問題が起きた。「画像の外側が未定義であることによる段差」が原因だとわかり、縁のピクセルを外側へ引き伸ばしてから処理する定番の対策で解消した。
- 砂の粒状感を出すためのノイズ処理が最初は強すぎて「テレビの砂嵐」のように見えてしまったため、少しぼかして薄くする調整を行った。これらはすべて、PreviewToolで生成した画像をこのセッション内で確認しながら調整できた（実機を使わずに見た目の方向性を詰められた、`docs/20-app3-feasibility-review.md`5章で提案していた「まず静止画プロトタイプで陰影の方向性を確認してから、実機での物理・傾きの調整に進む」という2段階の進め方どおり）。

### ビルド確認について

1本目・2本目と同様、このセッションではXcode/シミュレータをローカルで動かせないため、`git push`後にGitHub Actions上のビルド結果で確認した。今回はXcodeGenで生成したプロジェクトファイル自体に、2ターゲット（アプリ本体とPreviewTool）が同じ`Core/`フォルダを共有する構成に起因するパス解決の不具合が最初の2回のビルドで見つかり、フォルダ構成を整理して解消した（詳細はコミット履歴参照）。また、Swiftの新しい並行処理（アクター）まわりのコンパイルエラーも数点見つかり修正した。最終的に3回目のプッシュでビルド・全33件のユニットテスト・署名なしIPAの生成・PreviewToolによる陰影プレビュー画像の生成のすべてが成功した。

- `SandGardenApp-app-bundle`: デバッグ用の生の.app

### 陰影表現の見え方について（正直な評価）

`CIHeightFieldFromMask`＋`CIShadedMaterial`という組み込みフィルタの組み合わせで、「玉が通った跡が溝として彫れ、片側にハイライト・反対側にシャドウがつく」という狙った見た目には実際に近づけた。特に黒い砂（黒曜石・火山砂スタイル）では、溝の片側が明るく光り、反対側が暗く沈む立体的な質感がはっきり見える。明るい色の砂（白い禅砂）は色のコントラストが弱く、溝がやや控えめに見える。砂の粒状感（ノイズ）は現状やや強めで、今後実機で見ながら微調整する余地がある。自作CIKernelへのフォールバックは、現時点では不要と判断している。
