# QAレビュー: アーカイブ日付表示の変更・「今日」タブの横スワイプ（fac06c9, 6d1d5be）

対象コミット: `fac06c9`（本体）, `6d1d5be`（テストの時刻帯・タイムゾーン修正）
レビュー方法: 差分と周辺コード（ArchiveDayDetailView / DailyRingPanel / DailyRingStore / CalendarArchiveView）の読み込み。GitHub Actions run 37934241891（成功）を前提とする。ローカルではxcodebuildを実行していない。コードは修正していない。

## 総評

**データ破損につながる欠陥は見つからなかった。** ページ配列は全経路で「追加のみ」になっており、過去の「絵が半分ずつ混ざる」不具合の再発リスクは設計上低い。ただし、(a) 日付をまたぐ瞬間の今日ページの扱い、(b) 過去ページ表示中のスタイルメニューのロック通知が見えない、(c) 大見出しタイトルとスワイプの相性、は実機確認が必要。重大な指摘はなし。

## 重大

該当なし。

## 中

### M1. 過去日ページでスタイルメニューのロック通知が見えない（取り違え）
`styleMenu` は過去日ページ表示中も表示され、プロ未解除でスタイルを選ぶと `store.showLocked(.artStyles)` を呼ぶ。この `store` は**今日ページのstore**なので、お知らせ（notice）は画面外の今日ページにだけ出る。過去日を見ている間は何も起きないように見える（反応なしに見える）うえ、今日に戻ったときに古い通知が残って表示される。
- 再現: プロ未解除で、今日タブを左スワイプして前日へ → 右上のスタイルメニュー（キラキラ）から標準以外を選ぶ。
- 期待: ロックの案内が見える、または過去日ではメニュー自体を出さない／選択時にその日のページ側に案内を出す。
- 実際（コードから推定）: 無反応。今日に戻ると案内が出ている。
- 参考: 解除済みの場合は `styleRaw`（@AppStorage）を書き換えるので、全ページに反映され問題ない。

### M2. 日付をまたいでアプリを前面のまま使い続けた場合、「今日」ページが新しい日の扱いに食い違う（影響は小さいが、日記の書き込み先に関わる）
`todayDate` と `pageDates` を更新するのは `scenePhase == .active` になったときだけ（`handleDayChangeIfNeeded`）。アプリが前面のまま0時を越える（画面点灯のまま放置など）と、以下が起きうる。
1. `DailyRingPanel` の `diaryDate` は、今日ページ（`store.date == nil`）では `Date()` から毎回計算されるので、0時を越えると新しい日に切り替わり、`.task(id: diaryDate)` が新しい日の日記を読み込み直す。一方でタイトルは「今日」、ページのタグ・`todayDate` は古い日のまま。
2. その状態で `currentDate` や `history.revision` が変わると、`extendedPageDates` は「今日（古い日）の翌日」を `isDateNavigable`（`now = Date()` で判定）で通してしまい、新しい今日が**過去日用の `ArchiveDayPage`** として末尾に追加される。そのページは期間ピッカーなどのない過去日表示になる。次回の前面復帰で `pageDatesAfterDayChange` は「すでにある」ので何もせず、`todayDate` だけ更新され、ページが今日パネルに切り替わって自己修復する。
3. 日記テキストが別の日に混ざる経路: キーボードで入力中に0時を越えると、`diaryDate` が切り替わってから `loadDiaryAndSuggestIfEmpty` が走るまでの極めて短い間に、入力された文字が新しい日付に保存される可能性が理論上ある（実際には秒単位の入力でも成立しにくく、既存からある問題で、今回の変更で悪化はしていない）。
- 推奨（任意）: 今日パネルの `diaryDate` を、表示を作った時点の日付（`todayDate`）で固定する、または `NSCalendarDayChanged` 通知で `handleDayChangeIfNeeded()` を呼ぶ。
- 実機確認: 夜11時台にアプリを開いたまま画面をつけっぱなしにして0時を越え、タイトル・絵・日記の内容が食い違わないか（確認が大変なら、優先度は低い）。

## 軽微

### L1. 「ページ配列は追加のみ」について（確認結果: 問題なし）
- `DailyRingView` の `pageDates` を書き換える箇所は、`onChange(currentDate)`、`onChange(history.revision)`（どちらも `extendedPageDates`＝追加のみ）と、`handleDayChangeIfNeeded`（`pageDatesAfterDayChange`＝末尾追加のみ、テストあり）の3か所のみ。削除・並び替え・作り直しはない。
- 「今日に戻る」は `currentDate = todayDate` だけで配列を触らない。アニメーションなしで、`withAnimation` も使われていない。
- 前日追加は先頭への `insert(at: 0)`。これは `ArchiveDayDetailView` と同じ既存方式で、過去日に実機で問題がなければ同等。ただし先頭挿入で表示中ページの位置がずれる挙動が出ないかは、実機で連続スワイプして確認したい（下記の確認手順）。
- 日付変更時の `todayDate` 更新で、古い今日のページが `DailyRingPanel`（今日store）から `ArchiveDayPage`（日付store）に分岐が切り替わり、そのページの内容は作り直される。これは配列の変更ではなく表示ページ1枚の差し替えなので、前面復帰の瞬間（スワイプ中ではない）に限れば許容できる。
- `wasViewingToday` のとき、`pageDates` 追加と `currentDate = newToday` が同じ更新内で行われる。新ページへの移動がアニメーションつきで起きる可能性はあるが、配列は追加のみなので絵の混ざりは起きにくい。

### L2. 長期間（8日以上）アプリを開かなかったあとのスワイプで、日付が飛ぶ
`pageDatesAfterDayChange` は、前回の最終日との差が8日以上だと新しい今日だけを末尾に追加する。そのため、新しい今日から左へスワイプすると、間をすっ飛ばして古い今日（数日〜数週間前）に移る。間の日はそもそも `isArchiveAvailable` が偽（履歴保持期間外・保存なし）のことが多いので実害は小さいが、保存済みの日があればスキップされる。再起動すれば `init` で作り直されるため、実際にはアプリが何日もプロセスごと生き続けた場合のみ。許容範囲。

### L3. キーボード「完了」ツールバーの重複について
各 `DailyRingPanel` が `ToolbarItemGroup(placement: .keyboard)` を持つ。キーボード用のツールバーはフォーカス中のテキスト欄に紐づいて出るUIKit側の仕組みなので、隣のページが先読みされていても、通常は「完了」が2つ並ぶことはないと推測される（`ArchiveDayDetailView` でも既に同じ構成）。ただし、SwiftUIの `TabView(.page)` 内でツールバーが親の `NavigationStack` のツールバーと合流する挙動は実装依存でコードからは断定できない。実機確認項目に入れる（下記）。キーボード「完了」が複数出る場合は、`diaryFieldFocused` を持つページだけで `.toolbar` を出すよう条件付けすれば対処できる。

### L4. `@FocusState` とページ切替
`diaryFieldFocused` はパネルごとの独立した状態で、日記テキスト（`diaryText`）も各パネルが自分の `diaryDate` で読み書きする（過去日はstoreの固定日付、今日だけ `Date()` 計算。M2参照）。ページ間で状態を共有する経路はなく、スワイプ先の別の日に書き込まれる経路は見当たらない。スワイプ中にキーボードが出たままだと、キーボードが開いたまま隣ページに移りうるが、表示上の問題のみ（書き込み先は元のページの日付のまま）。

### L5. 大見出し（`.large`）タイトルとスワイプの相性（要実機確認）
`navigationBarTitleDisplayMode(.large)` に変更した。ScrollView が `TabView(.page)` の内側にあり、ナビゲーションバーのスクロール連動（縦スクロールで大見出しが小見出しに縮む）が効かず、常に大見出しが画面の上部を占めて、リング・日記の表示領域が以前より狭くなる可能性がある。逆に、縮む動作自体は問題なし。小さい画面（iPhone SE 3rd）で日記カードが見切れないか確認したい。

### L6. ヒント表示の常時確保領域
「← スワイプで前日へ」は、透明にしても高さ（約20pt）を常に確保する。意図的な設計（レイアウト変動の防止）だが、一度スワイプしたあとも余白が残り、今日ページの絵が少し小さくなる。気になれば、非表示のかわりにヒントを絵の上に重ねる（overlay）形にすれば領域を使わない。

### L7. カレンダーのセルサイズ
- 丸46pt、数字は丸の下（2pt間隔・高さ14pt固定）。空白セルも `46+16=62pt` なので、行の高さは揃う。
- コメントの「1列あたり約48pt」は不正確。幅375pt（iPhone SE 3rd / mini 等の最小サポート端末。iOS 17必須なので320pt端末は対象外）で、左右padding16×2 と列間隔8×6 を引くと1列あたり約42pt。丸46ptは列より約4pt広く、隣の丸との間隔は約4ptまで詰まる（重ならないが、以前の44ptより詰まる）。見た目が窮屈なら44pt以下にする。コメントも修正したい。
- `.buttonStyle(.plain)` に変えたため、未来日（`.disabled`）の見た目が従来と変わる可能性。数字は明示的にsecondary色なので判読性は問題ない。
- 数字の `font(.system(size: 11))` は固定サイズでDynamic Typeに追従しない。`frame(height: 14)` との整合は取れており、大きい文字サイズでも崩れない（その代わり拡大されない）。
- 暗幕とカプセルの撤去は意図どおり。今日はアクセント色の枠＋数字の太字・アクセント色のみで、サムネイルの形は何も遮らない。

### L8. テストの実行日依存性（確認結果: 依存なし）
- 新規3テストはいずれも固定日（2026-09-19）と、Asia/Tokyo固定の `calendar` を使い、`Date()` を使っていない。`isArchiveAvailable` を使う部分も `now` を固定して渡している。6d1d5beの `$0 <= today` / `$0 == today` への修正と、`pageTitle` への `timeZone` 付与で、UTC実行環境の揺れも解消済み。
- ただし `pageTitle` の `DateFormatter` 生成は都度生成で、`body` から毎回呼ばれる（軽微な性能面のみ）。
- テストでカバーされていないもの: 実際のスワイプ・ページ遷移、`handleDayChangeIfNeeded` の分岐（`wasViewingToday`）、M1/M2のような取り違え。純粋ロジックのみが対象で、UI挙動は実機頼み。

### L9. 今日ページの既存機能の退行確認（コードの範囲では退行なし）
- 期間ピッカー・普段と比べる: `DailyRingPanel(store:)` が `store.isToday` で表示を切り替える既存ロジックのまま。今日ページは常に今日store。
- 更新ボタン・レポート: ツールバーは `isViewingToday` のときだけ今日storeに作用するボタンを出し、過去日表示中は出さない。取り違えなし。
- scenePhase復帰: `handleDayChangeIfNeeded()` のあと `store.refresh()`。今日storeは日付変更後も `date == nil`（その時点の `Date()`）なので古い日のまま残る問題はない。過去日ページの `ArchiveDayPage` は前面復帰では再取得しない（`ArchiveDayDetailView` と同様）。
- `styleMenu` のチェックマークは `store.style` から `styleRaw` ベースに変更。過去日表示でも正しく反映される。この変更自体は妥当。
- `ReportView(style: store.style)` はそのまま。
