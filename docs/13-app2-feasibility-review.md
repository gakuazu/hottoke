## 結論（先に要点）

**技術的には実装を進めて問題ない。** ARKitの顔トラッキング自体はApple標準APIで枯れた技術であり、1本目で実証済みのGitHub Actionsビルド＋Sideloadly配布の枠組みもそのまま使える。ただし、1本目と比べて「**GitHub Actionsでは核心部分（実際の表情検出の挙動）がまったく検証できない**」という1本目にはなかった制約があり、これを前提に設計・開発の進め方を調整する必要がある。以下、懸念点と具体的な提案を含めて詳述する。

仕様書・ワイヤーフレームの完成度は高く、大きな手戻りが要る指摘はない。軽微な仕様の明確化（3点、6章参照）を提案する。

## 1. ARKit `ARFaceTrackingConfiguration` をSwiftUIに組み込む際の技術的な難所

### 1.1 SwiftUIへのラップ方法

- `ARSCNView`（SceneKitベース）か`ARView`（RealityKit）をARKitのホストビューとして使い、`UIViewRepresentable`で1回ラップすればSwiftUI側からは通常のViewとして使える。顔トラッキングはSceneKitの3D表示自体は不要（検出値だけ使う）なので、軽量な`ARSCNView`で十分。
- 表情の検出値（ブレンドシェイプ）は`ARSCNViewDelegate`の`renderer(_:didUpdate:for:)`（または`ARSessionDelegate`の`session(_:didUpdate:)`）で`ARFaceAnchor.blendShapes`を受け取る。これはカメラのフレームレートに近い頻度（最大60回/秒程度）で呼ばれるため、**SwiftUIの`@Published`プロパティへ毎フレームそのまま書き込むと描画負荷が上がる**。1本目の`KaleidoscopeDynamics`で行った「EMA平滑化＋間引き」と同種の対策を、入口（ブレンドシェイプ取得部分）に最初から組み込む設計が必要（3.2節の注意点そのもの）。
- ARKitのコールバックはメインスレッドではないことがあるため、UI更新前に`DispatchQueue.main.async`を挟む実装漏れに注意（1本目にはなかった新しいスレッド安全性の論点）。

### 1.2 シミュレータでは動作しない → GitHub Actionsでの検証範囲

- `ARFaceTrackingConfiguration.isSupported`はシミュレータでは常に`false`を返す（TrueDepthカメラのハードウェア有無で判定されるため、Xcode 15以降でシミュレータにカメラ機能が一部追加されても顔トラッキングは対象外）。これはGitHub Actionsのmacosランナー（Apple Siliconだが実機カメラなし）でも同様。
- 詳細は5章にまとめるが、要点は「**コンパイルが通ること・非対応機フォールバックが機能すること・ARKitに依存しない純粋ロジックのユニットテストが通ることはCIで確認できるが、実際の表情検出の挙動そのものはCIでは一切確認できない**」。1本目の`CMPedometer`もシミュレータで実データは取れなかったが、模様の描画ロジック自体（CoreImage/Metal）はシミュレータ上で本物同様に動いて検証できていた。2本目は「入力元（カメラ）」だけでなく「検出結果を使うゲームロジックの手前」までがARKit依存になりやすいため、後述5章のとおり**意図的にARKit依存部分とゲームロジックを分離する設計が1本目以上に重要**。

### 1.3 セッションの共有・ライフサイクル管理

- ワイヤーフレームでは「FacePreviewMonitor」が複数画面（ホーム以降の全ゲーム画面）で共通コンポーネントとして再利用される想定になっている。画面遷移のたびに新しい`ARSCNView`・新しい`ARSession`を作り直すと、毎回カメラ起動のラグ（1秒前後）が発生し体感が悪くなる。
- `ARSCNView`は`session`プロパティに外部管理の`ARSession`を後から差し替えられるため、「顔トラッキングを1つだけ持つ共有サービス（例: `FaceTrackingService: ObservableObject`）」を用意し、各画面の`ARSCNView`はその共有`ARSession`を指すようにする設計を推奨する。これにより画面遷移時の再起動ラグを避けられる。
- アプリがバックグラウンドに回ったとき・ゲーム画面から離れたときにセッションを`pause()`する実装も必須（プライバシー・電池消費・審査上の印象の両面で重要。6.4節のプライバシー説明と実装を一致させるため）。`scenePhase`の監視で対応可能。

## 2. 3つのミニゲームの実装難易度の見立ての妥当性

仕様書の「低〜中」という見立ては総じて妥当だが、ゲームごとに以下の補足がある。

### ①笑顔ジャンプ（連続値マッピング型）— 低、見立てどおり

- `mouthSmileLeft`/`Right`の平均値→ジャンプ強度という単純な連続値マッピング。ゲーム本体（自動ランナー＋障害物）はSpriteKitの`SpriteView`をSwiftUI内で使うか、`TimelineView`＋`Canvas`での自作のどちらでも実装できる（1本目の`KaleidoscopeCanvasView`で`Canvas`ベースの毎フレーム描画は実績あり）。見立てどおり低難易度。

### ②表情ビンゴ（複数お題並列判定型）— 低〜中。仕様書の「低」は一部楽観的

仕様書2.1節は「既存の閾値検出ロジックをそのまま複数お題に並列適用するだけ」としているが、**ワイヤーフレーム（`docs/09-app2-design.md`）で列挙された9マスのお題（笑顔/左右ウインク/口開け/眉上げ/びっくり目/大笑い/両目パチ/にっこり）を見ると、単一ブレンドシェイプの単純な閾値判定では済まないマスが混ざっている**。

- 「びっくり目」は`jawOpen`＋`eyeWideLeft/Right`＋`browInnerUp`の複合判定（仕様書2.2節⑥「表情コピー」がv2に回された理由として挙げた「複数ブレンドシェイプの組み合わせ判定」と技術的に同種）。
- 「大笑い」「にっこり」「笑顔」のように強度の違いだけで区別するマスが並ぶと、閾値の設定次第で1回の笑顔で複数マスが同時に開いてしまう・あるいはヒステリシス（一度開いたら閉じない、閾値の上下に余裕を持たせる）の細かい調整が必要になる。

「並列適用」の並列判定ロジック自体（3x3グリッドをループして各マスの判定関数を呼ぶ、縦横斜め8パターンのビンゴ判定）は確かに単純で低コストだが、**9マスの判定関数そのものには単純な閾値検出と複合判定の両方が混在しており、難易度は「低」ではなく「低〜中」と見るのが実態に近い**。v2の⑥「表情コピー」と技術的に地続きの部分が②にも一部混入している点は、後述6章で仕様側への確認を提案する。

### ③ウインク・シューティング（左右判定型）— 低〜中、見立てどおり

- 判定ロジック自体（片方が閾値超・もう片方が閾値未満）はコードとしては単純。ただし仕様書6.2節が指摘するとおり、自然な瞬き（両目同時）との誤判定回避の閾値チューニングは反復作業になる。1本目の数値チューニング（`KaleidoscopeDynamics`）と異なり、**このチューニングは実機での「自分の顔」でしか検証できず、合成テストデータだけでは詰めきれない**点が1本目より工数が見積りにくい要因。3往復程度の実機フィードバックは見込んでおくのが安全。

## 3. ワイヤーフレームの画面構成のSwiftUI実装容易性

- NavigationStack・2タブのTabView・グループ化リスト・sheetモーダルはいずれもSwiftUI標準コンポーネントで無理なく実装できる（1本目の`RootTabView`等と同じ作り方で対応可能）。
- 独自コンポーネント4点について：
  1. **FacePreviewMonitor**（丸型カメラプレビュー＋アイコン＋活性度バー）: `UIViewRepresentable`でラップした`ARSCNView`を`clipShape(Circle())`で丸く切り、その上にSwiftUIのオーバーレイ（アイコン・バー）を重ねるだけで実現できる。技術的な難所はARKit連携部分（1章）であり、見た目の実装自体は容易。
  2. **ビンゴセル（活性度ミニバー＋開閉状態）**: FacePreviewMonitorの活性度バーのロジックを縮小転用するという設計意図どおり、単純なSwiftUI View（`ProgressView`相当の自作バー＋開閉で`Image`を切り替え）で十分。
  3. **左右ペアの目インジケーター**: 2状態のトグル表示のみで、実装コストはごく小さい。
  4. **2本バー比較チャート**: 横棒2本の比較のみで、`GeometryReader`と矩形で十分。Chartsフレームワークのような外部依存は不要。

結論として、ワイヤーフレームの画面構成自体に「SwiftUIで無理がある」要素はない。唯一の技術的複雑さは「ARKitという入力源をどう共有・平滑化してSwiftUI側に渡すか」という1章の論点に集約されており、画面デザイン側の問題ではない。

## 4. 非対応機フォールバックの信頼性

- `ARFaceTrackingConfiguration.isSupported`はstaticプロパティで、呼び出すだけならクラッシュリスクはない。**重要なのは「このチェックを通過する前にAR関連のAPI（`session.run()`、カメラ権限リクエスト）を一切呼ばない」という実装規約を徹底することそのもの**であり、チェック自体は確実にクラッシュを防ぐ。
- 1点、ワイヤーフレーム・仕様書に明記が見当たらない分岐がある: **「端末はTrueDepth対応（`isSupported`はtrue）だが、カメラ権限をユーザーが拒否した」場合の画面**。この場合は非対応機フォールバック画面とは別に、「権限が許可されていません。設定アプリから許可してください」という案内＋設定アプリへのディープリンク（`UIApplication.openSettingsURLString`）が必要になる。3章の「非対応機フォールバック画面」と2章「オンボーディング」の間に、この権限拒否時のリカバリー表示が仕様上暗黙的に必要になっている点を6章で指摘する。
- もう1点、iOS 17をデプロイメントターゲットにする場合（1本目と同じ方針を想定）、iPhone Xは既にiOS 17非対応（iPhone XS以降が対象）なので、フォールバック画面の説明文言「対応機種（iPhone X以降）」は実質的に「iPhone XS以降」に読み替える必要がある（軽微な文言の確認事項、6章）。

## 5. GitHub Actionsのビルド確認で検証できる範囲・実機必須の範囲（1本目との違い）

### CIで検証できること（1本目と同様の仕組みがそのまま使える）

- `xcodebuild build -destination "generic/platform=iOS Simulator"`: ARKit/SceneKitのimportを含むコードのコンパイル確認。システムフレームワークのため追加のリンク設定は不要（1本目同様、XcodeGenの標準設定で足りる見込み）。
- `xcodebuild test`（シミュレータ）: アプリがシミュレータ上で起動してクラッシュしないことの確認。`isSupported`が確実に`false`を返すシミュレータ上で、**非対応機フォールバック画面が正しく表示され、そこで安全に止まること自体がテストになる**（1本目にはなかった検証価値）。
- ARKitに依存しない純粋ロジックのユニットテスト: 「ブレンドシェイプの値（`[String: Float]`や自作enumをキーにした辞書など、ARKit型に直接依存しない形）を受け取って、閾値判定・EMA平滑化・ビンゴ判定・スコア計算を行う関数」を**ARKitと分離した形で実装すれば**、1本目の`KaleidoscopeLogicTests`と同じやり方で合成データを使ったユニットテストがCIで実行できる。これは1章1.3節・本節の両方で触れた「ARKit依存部分とゲームロジックを分離する」設計判断が効いてくる部分であり、実装時の最重要方針として提案したい。
- 署名なしIPA化: 1本目と全く同じ仕組みがそのまま使える。

### CIでは検証できない・実機必須になること（1本目との最大の違い）

- **表情検出の実際の挙動そのもの**（カメラ映像→ブレンドシェイプの値が自分の表情にどう反応するか）。1本目は`CMPedometer`がシミュレータで実データを返さなくても、模様の描画ロジック自体はシミュレータ上で本物と同じ計算・同じ見た目を再現できていた（入力データを差し替えればCIでも見た目の検証ができた）。2本目は「入力（カメラ映像）→検出（ARKit内部処理）→数値（ブレンドシェイプ）」の経路そのものが現実のTrueDepthハードウェア無しでは一切発生しないため、**このアプリの核心（表情操作の感触）はCIでは原理的に一切確認できない**。
- 閾値・感度のチューニング（②③で特に重要）は実機での試行が必須。1本目のように「合成データを差し替えて机上で確認→実機で微調整」という順序ではなく、**2本目は最初から実機での繰り返し確認が前提になる**（実機ラウンドトリップの回数が1本目より多くなる見込み）。
- カメラプレビュー表示・権限ダイアログのフロー・メガネ/マスクの影響（仕様書6.3節）も実機確認が必要。

### 実機への依存を減らすための提案（推奨、必須ではない）

- DEBUGビルド限定で「スライダーで仮のブレンドシェイプ値を操作できるモック入力モード」を用意すると、ゲーム側のロジック（ビンゴ判定、スコア計算、UIの反応）を実機無しでシミュレータ上で目視確認できる。ARKitの検出精度そのものは確認できないが、「検出された後のゲーム側の挙動」の確認サイクルを大幅に短縮できる。1本目には無かった工夫だが、実機ラウンドトリップが増える2本目では投資価値があると考える。ユーザーへの追加コストはなし（外部サービス不要、デバッグ専用コード）。

## 6. 懸念点・仕様修正の提案

1. **②表情ビンゴの9マスのお題を、単一ブレンドシェイプ判定と複合判定（「びっくり目」等）に仕様書上で明示的に分類してほしい。** 2.1節の「既存の閾値検出ロジックをそのまま転用」という記述は一部のマス（笑顔・左右ウインク・口開け・眉上げ）には当てはまるが、複合判定のマスはv2⑥「表情コピー」と同系統の実装になる。実装コストの見積りとしては大きな問題ではないが、「低」という難易度表記を「低〜中」に直すか、複合判定マスの数をMVPでは絞る（例: 単一ブレンドシェイプ判定のマスのみ9マス分用意し、複合判定は次バージョンに回す）かの判断を仕様側で明確にしてもらえると実装がスムーズ。
2. **カメラ権限を拒否した場合のリカバリー画面をワイヤーフレームに追加してほしい。** 「非対応機（`isSupported=false`）」と「対応機だが権限拒否」は別の状態であり、後者には「設定アプリで許可してください」という案内＋ディープリンクが必要。3章の画面リストに1画面（または既存画面内の1状態）として明記を提案する。
3. **フォールバック画面の対応機種表記「iPhone X以降」を、実際のデプロイメントターゲット（1本目と同じくiOS 17を想定するなら実質iPhone XS以降）と整合させてほしい。** 軽微だが審査・ユーザー説明の正確性のために確認事項として残す。

上記3点はいずれも実装を止めるものではなく、実装と並行して仕様側で確認・微修正すれば十分と判断する。

## 7. 次のステップ（提案）

- 本レビューの内容（特に6章の3点）をux-designer・product-researcher側にフィードバックし、了承が得られれば実装着手に進める。
- 実装時の技術方針（このレビューで提案した内容）:
  - ARKit依存部分（`FaceTrackingService`）とゲームロジック（閾値判定・ビンゴ判定・スコア計算）を明確に分離し、後者はARKit型に依存しない入出力にしてユニットテスト可能にする。
  - `ARSession`は共有サービスで1つだけ持ち、画面遷移時に作り直さない。
  - `isSupported`チェックとカメラ権限拒否時のリカバリーの両方を、AR関連APIを呼ぶ前のゲート処理として一箇所に集約する。
  - Xcodeプロジェクトの配置（1本目の`app/HottokeApp.xcodeproj`とは別プロジェクト・別GitHub Actionsワークフローにするか、同一リポジトリ内の別ターゲットにするか）は実装着手前にユーザーへ確認する（本レビューの範囲外の判断事項）。
